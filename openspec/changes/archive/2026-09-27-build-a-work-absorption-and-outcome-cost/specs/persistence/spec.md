## MODIFIED Requirements

### Requirement: Sale integrity rows match live mutations
Committed conversational sale, cash-count, and close-confirmation mutations MUST keep `sales.sale_sessions`, `sales.sale_items`, `sales.payments`, `operations.operational_days` referenced by those sessions, `operations.cash_counts` referencing those days, `operations.closing_snapshots` referencing those days and current counts, `operations.work_items` referencing those days, `operations.outcome_runs` referencing those days, `operations.work_absorption_records` referencing those outcome runs, `operations.outcome_costs` referencing those outcome runs, related `audit.audit_events`, `platform.outbox_events`, and `platform.idempotency_records` transactionally consistent. Test/reset helpers that remove those mutations MUST delete the related integrity rows in the same transaction, including `sale.totalize@1` / `sale.commit@1` / `operational_day.opened` / `closing.submit_cash_count@1` / `closing.confirm@1` / `work_item.created` / `work_item.resolved` / `outcome_run.created` / `outcome_run.status_changed` / `work_absorption.created` / `outcome_cost.created` audit, `sale.ready_to_charge` / `sale.confirmed` / `payment.recorded` / `operational_day.opened` / `cash_count.recorded` / `closing.confirmed` outbox, and `lumo.message.totalize_sale` / `lumo.message.commit_sale` / `lumo.message.record_cash_count` / `lumo.message.confirm_close` idempotency. Helpers MUST delete `work_absorption_records` and `outcome_costs` before `work_items` before `outcome_runs` before `closing_snapshots` before `cash_counts` before `operational_days`.

#### Scenario: No orphan sale outbox
- **WHEN** a `sale.item.added`, `sale.ready_to_charge`, `sale.confirmed`, `payment.recorded`, `operational_day.opened`, `cash_count.recorded`, or `closing.confirmed` outbox row exists for a tenant
- **THEN** the referenced `sale_session_id`, `operational_day_id`, `cash_count_id`, `closing_snapshot_id`, and, when present, `sale_item_id` or `payment_id` MUST exist unless the entire mutation was rolled back (in which case the outbox row MUST NOT exist)

#### Scenario: Cleanup removes absorption and cost before outcomes
- **WHEN** the reset helper clears a tenant's mutations after a confirmed close
- **THEN** it MUST delete `operations.work_absorption_records` and `operations.outcome_costs` before `operations.work_items` before `operations.outcome_runs` before `operations.closing_snapshots` before `operations.cash_counts` before `operations.operational_days` in one transaction, no foreign-key error MUST occur, and no `work_absorption.created` or `outcome_cost.created` audit MUST remain

#### Scenario: Orphan checks cover outcomes
- **WHEN** the integrity check runs for a tenant
- **THEN** it MUST flag a cash count whose `operational_day_id` is missing, a broken `supersedes_cash_count_id` or `superseded_by_id` link, a supersede link pointing at a row with a different `business_id`, more than one current cash count for a day, a snapshot whose day or cash count is missing or in another business, a snapshot count whose day disagrees, more than one snapshot for a day, a `closed` day without exactly one snapshot, an `open` day with a snapshot, a referenced count that is not current, an internally inconsistent snapshot, an audit or outbox row referencing a missing `cash_count_id` or `closing_snapshot_id`, more than one OutcomeRun for a day and `daily_close_ready` version `1`, an OutcomeRun whose day is missing or in another business, a `completed` OutcomeRun whose `closing_snapshot_id` is not that day's snapshot, a `completed` OutcomeRun on an `open` day, an `open` day whose OutcomeRun is `completed`, an absorption row whose `outcome_run_id` is missing or in another business, more than one absorption row for the same `(business_id, outcome_run_id, task_type)`, more than one OutcomeCost for the same `(business_id, outcome_run_id)`, and an OutcomeCost whose `outcome_run_id` is missing or in another business

## ADDED Requirements

### Requirement: Alembic 0013 creates work absorption and outcome cost
Alembic revision id MUST be `0013_work_absorption_outcome_cost` and `down_revision` MUST be `0012_source_coverage_event_memory`. It MUST add `UNIQUE (id, business_id)` on `operations.work_items` when missing so optional absorption FK `(work_item_id, business_id)` can reference `operations.work_items (id, business_id)`. It MUST create `operations.work_absorption_records` with the columns, checks, unique key `uq_work_absorption_records_task` on `(business_id, outcome_run_id, task_type)`, composite foreign keys, indexes on `business_id` and `outcome_run_id`, closed `task_type` and execution-mode checks, non-negative integer checks on step and minute fields, nullable `business_intervention_seconds` and `internal_intervention_seconds` with `CHECK` that non-null values are `>= 0`, closed `automation_level` in `manual` / `assisted` / `automated`, and `jsonb_typeof(evidence_ids) = 'array'`. It MUST create `operations.outcome_costs` with one row per `(business_id, outcome_run_id)`, `currency` fixed to `USD`, nullable monetary amounts, nullable `business_intervention_seconds` and `internal_intervention_seconds` with the same non-null `>= 0` check, non-null `cost_completeness`, non-null `retry_count`, component status checks in `measured` / `estimated` / `unavailable`, and composite foreign key to `operations.outcome_runs (id, business_id)`. It MUST `ENABLE` and `FORCE` ROW LEVEL SECURITY on both tables, create policy `tenant_isolation`, and grant `lumo_app` `SELECT`, `INSERT`, `UPDATE`, and `DELETE`. It MUST create `BEFORE INSERT` and `BEFORE UPDATE` triggers on both tables that reject any statement when the owning OutcomeRun `status` is `completed`. It MUST NOT insert a row. It MUST NOT backfill closed days. Downgrade MUST abort when any absorption or cost row exists. Otherwise it MUST drop both tables and MAY drop `uq_work_items_id_business` only if no dependent FK remains. Schemas `workflow` and `memory` MUST NOT be created.

#### Scenario: Upgrade leaves tables empty
- **WHEN** Alembic upgrades from `0012` on a database with completed closes
- **THEN** the head revision MUST be `0013_work_absorption_outcome_cost`, both new tables MUST exist, and both MUST contain no row

#### Scenario: Downgrade with instrumentation aborts
- **WHEN** any `work_absorption_records` or `outcome_costs` row exists and downgrade from `0013` is attempted
- **THEN** the downgrade MUST abort and the rows MUST remain
